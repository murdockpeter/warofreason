# Design decisions

- 2026-10-25 (setting correction): Keep Maurice and Fontenoy/Tournai, 1745 central. Treat Waterloo solely as an operational mechanics source. Add `fontenoy-operational` / `maurice_operational_v0.1` with the actual 38-unit Maurice roster, Dutch/Anglo-Allied provenance, Fontenoy schematic places and configured edges, 1745 calendar, Maurice de Saxe/Cumberland and Tournai objectives. Public creation uses that profile and a saved Fontenoy setup can create an independent operational copy. Freeze mapped Maurice rosters into briefs and default result entry to Maurice. Retain old reference-profile IDs/receipts for compatibility; do not port Waterloo historical scenarios or special units. Per-unit aftermath and automatic siege/victory integration remain explicit follow-up work, while their existing Fontenoy workflow remains intact.

- 2026-10-25 (0.8.0 preparation): Add ordinary screens, deployment/recall, simultaneous withdrawal submissions and own-side HQ/zone overlays as an explicit schema-3 opt-in with `waterloo_preparation_v0.1`. Optional fields never materialize in old snapshots. Use one abstract screen per corps and manual parent-roster allocation; special historical detachments remain separate. Withdrawal uses three simultaneous 20-minute steps, unique friendly priorities, no corps pass-through, blocked/trapped blown outcomes and a full-phase hold. Other forces receive concurrent preparation credit. Organization precedes withdrawal. Review HQs/returns/charts before deploying screens or submitting retreats; allow the documented empty road-adjacent HQ fallback when its army has no on-map units. Preserve native cancellation, audit/replay and read-only faction disclosure boundaries.

- 2026-10-25 (0.7.0 playable slice): Implement aggregate schema 3 for the original Crossroads simultaneous hex campaign. Saved per-side orders lock independently, resolve in shared five-minute batches, and pause at required contacts. The neutral tactical bridge freezes rosters/chart context and reinforcement windows, supports reasoned arrival overrides, records manual results separately from approved effects, and preserves corrections with a conservative dependency guard. HQ placement and due return review use explicit commands. SQL 001/export format 2 remain; v1/v2 payloads/replays are unchanged. Crossroads cloning restarts the original opening scenario. A late battle delays the next planning window until its reviewed conclusion; fully concurrent next-phase battles, historical scenarios and detailed remaining rules stay on the backlog. See [implemented controls](WATERLOO_PLAY.md).

- 2026-10-25 (Waterloo design draft): Specify a separate `waterloo_simultaneous_v0.1` operational profile with original versioned charts, six-hour AM/PM defaults, timed repeated activations, private simultaneous submissions, batch collision resolution and a shared adjudication cursor. Reinforcement windows use the same campaign clock, with optional tactical-turn conversion and audited overrides. External tactical results remain manually entered and support superseding corrections with dependency-aware aftermath reconciliation. These are documented defaults for future implementation/playtesting, not current app behavior. See [the specification](WATERLOO_MOVEMENT_SPEC.md) and [backlog](WATERLOO_TODO.md); existing Fontenoy rules/saves are retained.

- 2026-10-22 (dossier refinement): Give formation intelligence its own rounded, double-edged report frame and original generic heraldic-style SVG emblem, with a stronger identity banner, readiness cards, paired composition/commander sections and refined roster typography. The emblem does not assert a historic unit insignia or disclose composition. Future formation illustrations can replace this visual area when commissioned; no asset storage or rules changes are introduced in this cosmetic increment. The existing projected-data and modal boundaries remain in place.

- 2026-10-22 (livery): Replace the cream/green interface with a medium-dark slate campaign desk: charcoal chrome, layered grey panels, warm cream text and muted brass actions/focus accents. Shared CSS tokens cover menus, forms, readers, rosters, split panes and feedback states, with dark native controls/scrollbars. French/Allied identity colours and the parchment map retain their meaning. Electron's initial window background matches the desk to avoid a cream flash during loading. Gameplay, data formats and independently generated printable briefs are unchanged.

- 2026-10-21 (map usability): Started campaigns reopen on the operational map. The permanent sidebar becomes a Campaign menu; administrative/setup/rules/help panels collapse, and selected-formation route controls stay above the map. Right-click/keyboard formation menus offer movement, hold, split, inspection and scouting without bypassing faction views, commitment locks or domain validation. A native modal with two roster panes supports explicit splitting.
- Splitting is a player-agreed campaign reorganisation, not an asserted Maurice rule. It requires active-side planning, no issued orders, no unresolved contact/battle and nonempty resulting formations. It transfers only existing source units/commanders, at the same square, with unchanged faction/concealment/unit facts. A validated operational command and `formation_split` event preserve atomic optimistic saves; journal recovery/import reconstructs the command from the one new formation and validates the exact transition. Existing SQL/document format versions remain unchanged. Modal drafts use the existing save/discard/close guards.

- 2026-10-21 (F): Campaign aftermath is an explicit opt-in extension using `house_rule_v0.1/aftermath-1`, not an official Maurice campaign engine. Versioned module defaults and a replaceable pure strategy registry support fixed-policy rebuilding or individual manual review. Regular rebuilding uses conscript quality only when allowed; opening quality is preserved for scenario validation and fresh setup clones. Irregular/artillery recovery follows explicit variants and never gains regular quality. Losses remain as roster records, and retired rest is configurable. No permanent disruption is inferred.
- Epic Points are nullable manual entries with a sum and missing-entry count; no official formula is approximated. Campaign exhaustion is independently entered, with no conversion from tabletop Army Morale. Post-battle squares and commander decisions require explicit review, without automated retreat/pursuit or card effects. Arrivals, statuses and friendly attachments are journaled; unavailable officers detach.
- F pauses operations after both faction phases. Only explicit completed-turn finalization processes due recoveries, supplied investment progress and victory, once. Unresolved contacts/battles/reviews prevent finalization; final-turn battles can still finish before evaluation. Only ready-unit columns create new contacts or block movement, preventing empty/lost/recovering rosters from producing impossible battles.
- Investment/supply/relief are persistent umpire attestations, not inferred map connectivity. Initial proposals: supplied investment +1, siege threshold 6, campaign exhaustion threshold 10, deadline fallback Allied, conflicting substantive claims draw. All values/outcomes are configurable. A substantive claim takes precedence over the deadline fallback; opposing simultaneous claims use the configured conflict result. No victory is committed before a completed-turn checkpoint. Outcome reasons and rule/condition snapshots are retained, then strategic play is locked.
- F retains aggregate 2/export 2/SQL 001 with optional fields and replayable action receipts, preserving old snapshots. Confirmed battle effects, turn finalization and commander status use native default-Cancel dialogs. Drafts survive navigation/cancellation/errors. Clone removes play history and restores opening unit qualities/readiness and active commander statuses. Detailed timing and provenance are in [CAMPAIGN_AFTERMATH.md](CAMPAIGN_AFTERMATH.md).

- 2026-10-21 (E): Scouting is umpire-adjudicated. Defaults live in `tabletop.v0.1.json`: range 1, lifetime 1 turn, one attempt per column/turn, and ready cavalry/irregular-infantry eligibility. All are campaign house rules; a physical/app d6 and agreed modifier are recorded without inventing an official success table. Scouting does not automatically consume movement points.
- Intelligence is a dated snapshot with unknown/located/estimated/identified disclosure. The latest observer/target report supersedes older reports, including unknown results. Expiration never revives an older report. Hidden targets are shown at the observed square, without live tracking; exact rosters/commanders are disclosed only after explicit identification.
- Battle declarations use a real unassigned contact candidate. Both primary columns begin on table; participants must have ready units and be within the configured orthogonal joining range (default 1 square, stored in the same versioned JSON). Reinforcement arrival instructions and entry edges are manually agreed, not a replacement for Maurice tactical setup. Declarations freeze participants and prevent overlapping commitment.
- E records result facts only: decisive/marginal/draw, per-unit broken/retired/survived/not-engaged, optional final disruption, commander reports and per-battle Army Morale. Results require explicit confirmation and are immutable. No loss/recovery/quality/commander/siege/victory effect is applied. Columns stay held pending F.
- Tabletop state is an optional aggregate-v2 extension. Events carry a typed command receipt, generated identity and timestamp for deterministic replay during recovery/import. Existing snapshots are untouched, and clones remove tabletop/operational state. Journal object comparisons now ignore JSON member order while preserving array order; serialized object order cannot change the meaning of a saved action.
- Printable briefs are generated in main from saved frozen snapshots only, never renderer HTML or a renderer-supplied path/URL. All user text is escaped. HTML is offline with a restrictive CSP; PDFs use a temporary hidden sandboxed renderer with no preload/Node and are written atomically after a native save dialog. Both documents intentionally contain both sides and remain umpire/shared-table outputs.

- 2026-10-21 (D): Operational play is an explicit optional aggregate-v2 extension, preserving legacy saves and immutable snapshots. Enabling adds versioned movement defaults from `operations.v0.1.json`; it never silently starts movement for an existing campaign.
- D uses sequential faction phases: each faction gets one order/resolution phase before advancing the configured campaign day. Unordered columns hold. Orders are journaled before resolution and can return to planning; committed resolution cannot rewrite history. The final second-faction phase ends the campaign window without calculating victory.
- Movement is `house_rule_v0.1/operations-1`, not official Maurice: allowance 3, road cost 1, off-road cost 2, configured river-crossing surcharge 1. Values and blocked squares are adjustable before orders. Orthogonal steps only, no repeated squares, friendly stacking allowed, no undocumented terrain or commander bonuses. The illustration has no rules effect.
- An opposing occupied square cannot be traversed. A route ending there creates deterministic engagement candidates and stops in the preceding square, holding participants for Milestone E; no withdrawal, pursuit or tactical combat is invented. All operational commits include the rule ID/values in their journal reason and retain before/after snapshots.
- Faction projections omit concealed enemies and all enemy composition, commander names and orders. Dedicated faction exports use the same allowlist, exclude journal snapshots and are deliberately not importable campaign backups. Shared management screens require returning to umpire mode. This is local pass-and-play, without access control against an operator who deliberately selects umpire or inspects local storage.
- User preference: after the functional milestones, conduct a dedicated interface simplification pass. Keep current controls direct and accessible; defer visual redesign until the end-to-end tabletop workflow is available.

- 2026-10-21: Keep the existing repository root as the application root. Use small local CSS components rather than a large UI framework; Zustand holds only the active screen and transient diagnostic state.
- Use esbuild for explicit main/preload bundles and Vite for renderer assets. Pin installed dependency versions and commit the lockfile.
- License is proprietary/all rights reserved pending owner selection of an open-source license. No rights to Maurice materials are asserted.
- No campaign state or persistence in Milestone A. Diagnostic logs are local app diagnostics, not a campaign event journal. Reset only clears the session diagnostic notice, through a confirmation dialog.
- No provisional rule values or historical deployments have been implemented. Initial unit vocabulary validation follows the supplied plan; full campaign/reference validation belongs to B.
- 2026-10-21: Reload testing exposed Chromium `ERR_ABORTED` (-3) cancellations being reported as fatal load errors. Ignore cancellations and subframe failures; preserve the native alert for genuine main-frame load failures. Real Electron regression checks cover both paths.
- 2026-10-21: A local development screenshot exposed unstyled rendering: Vite injects CSS into style elements, blocked by `style-src 'self'`. Permit inline styles only in the development HTML transform. Production retains external CSS and the strict policy. Electron tests now assert computed flex/grid layout and sidebar color in development, built and packaged runs. The development assertion failed before this fix and passed afterward; the corrected development screenshot was visually inspected.
- 2026-10-21 (B): Use SQLite through bundled `node:sqlite` instead of the originally proposed `better-sqlite3`. Verified directly in pinned Electron 45.0.0 / Node 24.22.0, local Node 24.7.0, and actual packaged app. This avoids a separate native ABI/rebuild dependency. Local Node 24.7 still labels the API experimental; runtime upgrades require the same persistence tests.
- Store versioned validated aggregate snapshots plus relational journal/active-record links. Keep writes, journal insertion and active selection in one transaction. Reject stale revisions; never reset an unreadable or newer database.
- B creates only unconfigured draft campaigns. Scenario data, setup/start actions, dates, forces and house-rule settings remain C or later. Draft-only portable schema v1 is intentionally strict; future versions need explicit migrations.
- Archive is non-destructive and read-only. Cloning creates fresh IDs and a fresh seed, remaps all aggregate references, and records the source ID in a new journal. Import rejects duplicate IDs rather than replacing or silently renaming records.
- Export full saved state and journal via a native dialog, bounded to the same 20 MiB limit as import. Publish using same-directory temporary write, flush and rename. Uncommitted form edits are excluded. No player-facing fog-of-war exports are implemented yet.
- Private PDFs in `contextonly/`, like `reference/`, are ignored by Git and excluded from the package allowlist. They were not needed for persistence work and no source prose or art was incorporated.
- 2026-10-21 (C): Consulted the private Maurice Fontenoy scenario pages for numeric composition and contingent attribution. Encoded French 20, Dutch 7 and Anglo-Allied 11 as scenario-scale facts, with bibliographic references; no prose, images, cards or tactical effects copied. Historical context is corroborated by Royal Collection Trust RCIN 729096. See the sourced campaign specification.
- New campaigns seed a module-0.1.0 draft. Existing v1 drafts upgrade only on explicit module loading; IDs and old journal snapshots remain unchanged. Custom legacy entities are never overwritten. Configured aggregate schema 2 and export format 2 coexist with legacy imports/history; no destructive SQL table migration or bulk save rewrite is needed.
- All provisional opening splits, squares, commander attachments, concealment, schedule, siege defaults and objective descriptions live in the versioned module JSON. They are player-editable house-rule choices. No operational limits, movement costs, scouting tables, siege thresholds or victory rules are implemented.
- The original 12 × 8 SVG is a schematic umpire/setup view. Labels are approximate; no default road/river network is asserted. Proposed roads and scale can change without regenerating square IDs or assignments. Player-specific fog of war and interactive movement remain D.
- Start requires a saved validated setup plus explicit acknowledgement of the provisional setup/map and a default-Cancel native confirmation. Start sets only turn 1 and the chosen opening day/faction. Started setup is read-only; cloning remaps the full graph and creates a draft for new setup review.

## 2026-10-26 - simultaneous siege checkpoints

Opt in prospectively to `maurice_siege_v0.1`. Use explicit eligible calendar hours (source two-day cadence proposes 48 hours), retaining partial earned time across pauses. The umpire attests the whole interval since the last checkpoint, including overnight gaps, with an explanation; uncertain/partially eligible intervals are conservatively recorded as ineligible. No automatic supply-path or relief inference is introduced. Victory uses the completed checkpoint clock before overnight advancement; substantive opposing claims use the configured conflict result, and deadline fallback applies only with no substantive claim. Concluded campaigns are read-only, with immutable checkpoints and fresh-setup cloning. Cadence changes require zero carried eligible time. These are campaign adaptations awaiting human playtesting, not official Maurice mechanics.

## 2026-10-26 - simultaneous commander records

Commander management is an explicit optional campaign record, separate from tactical card rules and operational HQ ratings. Freeze the current roster/assignments at enablement as a reviewed clone baseline. Permit manual arrivals/details/status at clear planning or a settled checkpoint before siege review; restrict attachment changes to clear planning before orders and preparation submissions. Lost/retired officers detach, restored active officers remain unassigned, and no tactical loss or bonus is inferred. Later decisions invalidate dependent historical battle corrections while preserving old briefs. Fresh setup clones omit later arrivals and decision history. Private references remain own-side/umpire records and are not added to shared printed briefs. Helper mode offers optional planning/checkpoint review and returns to guarded officer drafts.

## 2026-10-26 - optional manual Epic Points

Use one versioned entry per applied battle, or separately identified named campaign events. Store each side's explicitly entered integer values or null for not recorded; derived totals include only the latest version of each entry. Corrections preserve original entries, reasons and source identity, with expected-version checks. Entry notes and event titles remain umpire-only; faction views show only own current values and generic source labels. Tracking is optional and never blocks phase finalization. Entries change no strategic or tactical mechanics, but advance the dependency guard so older battle effects cannot be silently revised across a scoring decision. Finish tactical corrections first and record final-phase points before campaign conclusion. These are app recordkeeping choices, not published Maurice scoring calculations.

## 2026-10-26 - simultaneous scouting and intelligence

Reconnaissance is a manual, optional campaign worksheet. A ready formation can request observation of a public map hex during its own unlocked planning, after preparation. Requests contain no hidden target identity. The umpire decides eligibility, range, attempts, physical dice, card interpretation and release level at the table; no success table or official Maurice mechanic is inferred. One unanswered request per formation per phase is a workflow guard, not a scouting allowance. Requests and report revisions are each bounded to 500 for storage.

Release no information, position only, an estimate or explicitly identified text. Player messages and identified details are deliberately entered for release; they never copy or join a live enemy roster. Each report has a fixed observation phase/clock, a manually chosen valid-through phase, a save timestamp and separate private rationale. Sequential corrections/withdrawals preserve the first observation clock, supersede only their own report and retain every earlier revision. New reports require a current-phase request; existing reports can be corrected at later settled planning/checkpoint windows. Expiry does not erase umpire history. Unanswered requests close at phase end without blocking orders or finalization.

Faction maps show their own current forces and only current unexpired report snapshots, instead of anonymous live enemy counters. Dated marker inspection and report cards consume a redacted projection; expired observation details, opposing requests, private rationale and old revisions are withheld. This is local pass-and-play filtering, not account authorization. Full campaign JSON and journals remain umpire backups. Older saves gain the optional ledger only on the first committed request; fresh setup clones omit it. Reconnaissance changes no units, HQs, movement, siege, morale or scores, but advances the dependency serial to prevent silent rewrites of earlier applied battle effects across later intelligence decisions.

## 2026-10-26 - map-first drawers

Keep the turn bar and map in the normal page flow. Group optional campaign administration in side drawers; use a bottom tray for route/order work and a compact expandable Helper line. Native details/summary keeps hidden content keyboard-accessible on demand and mounted without losing draft state; closing a sheet never means discarding an action. Use non-modal sheets so map clicks remain available. Keep one open sheet per edge, anchor side sheets below turn controls, and reserve map space for route trays. Saving/cancelling a route or completing a legacy resolution closes the corresponding tray; optional administration remains open until dismissed. Existing domain commands, validation, confirmations, faction projections and persistence remain authoritative.

## 2026-10-27 - historical OOB working baseline

Use the player-selected Wikipedia battle OOB as a working reference, alongside the main battle article for approach context. Further WDS screenshots are optional. Keep the battle-date roster distinct from campaign-opening returns, siege/garrison forces and arrivals; aggregate movements do not establish individual regiment assignments or coordinates. The supplied WDS map is scenario evidence with an unresolved date/scale, not verified operational geography.

Expose a searchable offline reference drawer first. Display source complements and hierarchy without asserting a combined army total or automatically converting battalions/squadrons into Maurice units. Preserve ambiguous allocations and alternative counts, use undated lookup aliases for later British identifiers, and keep all historical-to-game ratings/scaling/deployment work explicitly pending. Document data attribution separately from the application's code license. No current save is rewritten by browsing the catalogue.

## 2026-10-27 - manual adjudication alongside rules-assisted play

Use the same campaign state and validated command journal for rules-assisted and umpire-adjudicated outcomes. `manual-adjudication` records explicit formation/HQ placement, posture, descriptive reported strength, ready/lost availability of existing units and forward time within the present phase. It bypasses route/terrain calculations and automatic contact generation; it does not bypass identity, ownership, conservation, non-stacking or unresolved-work guards. Empty preparation may be waived; submitted preparation must be resolved. Manual phase completion opens the normal checkpoint; enabled siege/recovery policies and next-phase posture resets still require explicit phase finalization. See [Manual adjudication](MANUAL_ADJUDICATION.md).

Keep this layer available to the local umpire without a global mode switch, so rules-assisted turns and manual rulings can coexist. Rulings carry private rationale and before/after evidence; corrections append a new decision against current state. Never rewind the clock or overwrite earlier records. Bind each draft to its starting campaign revision, retain it across navigation/default-Cancel confirmations, and advance the dependency serial on commit. Scheduled unit recoveries retain their existing workflow rather than being silently cancelled. Reported strength is a descriptive estimate, never an inferred Maurice unit count or game modifier.

Manual placement creates a foundation for regional maps, but expanding geography, map scale, region identifiers/links, editing, online authorization and AI discussion integration remain separate work. Keep the current schematic and profile unchanged in this increment.

## 2026-10-27 - actionable order handoffs (0.15.1)

The compact helper must name the next action after an order lock. A locked faction with the other still planning receives the exact other-side Map view handoff; an umpire receives the corresponding Planning side choice. Explain empty hold orders and the subsequent switch to Umpire for Resolve simultaneous movement. When both sides are locked in a faction view, explicitly name the umpire-resolution step instead of a generic waiting state. Show me focuses the selector without changing the selected view, revealing opposing troops or committing an action. Local handoff and a separate opponent's waiting workflow remain explicit choices for the people playing.

## 2026-10-27 - persistent saved planning routes (0.15.2)

Render saved movement intent directly from submissions throughout planning and locked phases, independently of the active draft or selected formation. Show every saved segment with a faction-colored arrow and destination ring; distinguish an unsaved extension with a dashed gold path. Faction views receive only their own saved routes and draft overlays; umpire view sees both submissions. Remove planning arrows when resolution starts so they cannot be mistaken for actual travel or current positions. SVG overlays ignore pointer events and do not change the campaign, route validation, movement timing or journal format.

## 2026-10-27 - connect the historical OOB to playable formations (0.16.0)

Deliver the linkage as a separate historical regimental profile, retaining the original 38-unit Maurice scenario. Give each of the 143 catalogue regimental/aggregate organizations one persistent operational record, assigned once to 14 service/arm campaign formations. Retain reported battalion/squadron complements and source hierarchy without inventing subordinate identifiers or a battalion-to-Maurice-unit ratio. The profile begins on the battle-roster date, 11 May; deployment/grouping and tabletop scale are explicitly provisional.

Regular records propose trained as a house placeholder and permit an umpire to review/change regular ratings before accepting the setup. Never infer elite status from fame or mark the historical adaptation official Maurice. Require explicit scale/deployment/source-gap acknowledgements and a replayable review command before play. Full siege/garrison/pre-battle returns and structured splitting remain separate work. Existing campaigns are preserved; users deliberately create the historical campaign, and clones require a new review. See [Historical formations](HISTORICAL_FORMATIONS.md).

## 2026-10-27 - compare formations on a common grouping basis (0.16.1)

The original historical grouping pooled French infantry and horse nationally while splitting Allied arms by service, producing three versus eleven counters and materially different formation-level command packets. Supersede that default with common reported-subunit targets, preserving whole source brigades and unknown complements, while retaining all 143 organization identities. Do not infer equal manpower or combat power from counter counts. Expose source-size badges and an explicit preview/confirmed regroup action for old untouched setups; preserve progressed games and old journal replay. Deployment remains provisional and requires review.

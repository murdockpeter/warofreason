# Architecture

## Playable historical formation links (0.16.0)

`fontenoy-historical-profile.ts` seeds a separate `historical_fontenoy` creation profile under the existing Fontenoy operational module. It instantiates every leaf catalogue organization once (143 records) and assigns those UUIDs to provisional campaign groupings. Each unit's optional `historical` reference pins its catalogue, version and organization. `historicalProfile` stores the representation version, reviewed opening ratings and review metadata. The existing two operational coalition factions and command-army vocabulary remain; historical service/origin and source hierarchy come from the pinned identity, not the coarse command-army field.

Profile-specific validation preserves the original exact 38-unit/composition checks while requiring the complete historical identity set, canonical names/types, service ownership, house provenance and opening ratings for the new profile. Shared assignments, frozen briefs and recovery/result arrays accommodate the larger roster. Frozen units must retain the same catalogue identity/version as their current records. Regimental count and reported battalion/squadron complement remain distinct; no extra numbered subordinate identities are fabricated.

`historical-roster-review` is a validated, native-confirmed, replayable command required before other historical campaign actions. The renderer retains review drafts through the normal guarded slot. Regular grades are proposed trained placeholders until explicit review, with optional elite house choices; neither is inferred from reputation. Historical creation from an existing game creates a new campaign and enters umpire setup; it never rewrites the earlier aggregate. Clones remap campaign UUIDs, retain historical identities/opening grades, reset outcomes and require fresh review.

The reference catalogue component is memoized behind stable campaign/view/inspection props so unrelated draft keystrokes do not redraw its full table. Selecting a historical name opens the existing read-only dialog component, keeping source text out of narrow roster columns.

Formation inspection, assigned-roster lookup, saved orders and printed/frozen battle briefs resolve names, service, source complements and hierarchy from that shared identity. Metadata survives manual availability changes and rebuilding. No database migration or export-format bump is needed. See [Historical formations](HISTORICAL_FORMATIONS.md) for the operational/representation boundary and remaining full-campaign research.

## Manual adjudication (0.15.0)

`manual-adjudication-schema.ts` defines narrow ruling inputs and immutable before/after records. Optional aggregate-3 `adjudications` and optional corps `reportedStrength` preserve old-save shape; no SQL migration or export-format bump is required. `manual-adjudication.ts` applies rulings on the existing cloned-command boundary, enforces revision/phase/dependency/reference guards and validates record chronology. Commands and resulting state save atomically through the existing receipt/replay repository. Manual rulings advance the effect serial; previous frozen briefs remain unchanged and dependent battle corrections are blocked.

The renderer uses its existing guarded draft slot and native default-Cancel preflight. A map-interactive bottom drawer, right-click entry, proposed-position markers and helper target share session helpers in `manual-adjudication-session.ts`. Private rationale/history mount only in umpire view; friendly inspection and new battle briefs display escaped reported strength. Existing scheduled recoveries remain authoritative. Roster descriptions refresh for manually adjudicated games as well as aftermath-enabled games; the old behavior stays intact for prior profiles/journal replay. Setup clones omit manual history/strength and rebuild ready roster descriptions when cloning a manually adjudicated game. See [the manual layer guide](MANUAL_ADJUDICATION.md).

Record/approve preserve unit state; resolution at battle end applies formation and unit effects in the same repository transaction. Recovery occurs at explicit phase finalization after clock advancement. Existing last-effect/end-time correction guards protect unit baselines and replace only the corrected battle's recovery schedules. Ready-only new briefs preserve earlier frozen rosters; setup clones reset qualities/readiness and remove extension history. No SQL/export-format bump or silent save rewrite is introduced.

Army Morale and disruption are retained without inferring exhaustion or permanent tactical effects. Abstract screens do not allocate or duplicate named parent units. The first slice pauses publication at unresolved contacts, reserves committed forces, records external results without applying losses, and applies separately approved effects when the shared cursor reaches battle end. A cross-boundary battle delays the next planning window rather than allowing time to rewind. Corrections compensate only without later dependent effects; no later history is rewritten. Faction UI withholds enemy composition/orders and battle adjudication; the trusted renderer/database still contain the full pass-and-play record. See [available gameplay and remaining scope](WATERLOO_PLAY.md).

Milestones A–F establish an offline desktop shell, persistent campaign library, reviewed Fontenoy setup, operational play, scouting, a manual tabletop bridge and explicit aftermath/siege/victory. ## Boundaries

- `src/main`: Electron lifecycle, trusted-window IPC checks, native dialogs, local logging and the persistence repository. Owns all file and database access.
- `src/preload`: bundled CommonJS sandbox-compatible context bridge. Exposes named methods only; never exposes ipcRenderer, Node or paths.
- `src/shared`: Zod request/response contracts and DTOs used across the process boundary.
- `src/domain`: framework-independent vocabulary, versioned aggregates, module/schema validation, pure setup/operational commands, faction projection and portable journal validation. No tactical engine.
- `src/renderer`: React screens, accessible components and Zustand session/draft state. Components invoke store commands; domain validation and storage operations stay outside React. Imports no Node or Electron modules.
- `src/data`: versioned Fontenoy JSON: sourced numeric force facts, original schematic locations and explicitly provisional operational defaults. No private source material is shipped.

Vite bundles the renderer; esbuild bundles main and preload. TypeScript checks each boundary separately. Production uses local files and in-memory navigation state. The production CSP denies network connections; permissions, popups and document navigation are denied. Development permits the loopback Vite origin and its hot-reload socket; only development permits Vite's inline refresh preamble and injected style elements. Production uses bundled external stylesheets with `style-src 'self'`. Main validates both IPC sender and payload; preload validates returned DTOs.

## Persistence boundary

`CampaignRepository` is implemented by `SqliteCampaignRepository` using bundled `node:sqlite` in Electron main. Electron 45.0.0 (Node 24.22.0) and local Node 24.7.0 were directly checked for SQLite availability; built and packaged application tests also exercise it. This deliberately replaces the plan's proposed `better-sqlite3` driver, avoiding a separate ABI/native rebuild dependency while retaining SQLite and the repository boundary. Node 24.7 reports its SQLite API as experimental; runtime upgrades must rerun persistence and packaging checks.

Migration 001 is transactional and recorded both in `schema_migrations` and SQLite `user_version`. Unknown newer versions fail safely. Tables store validated campaign aggregate JSON, per-revision event snapshots, and a foreign-key-protected last-active campaign pointer. Aggregate references are validated in Zod; SQLite foreign keys protect the journal and active pointer. WAL mode, full synchronization and immediate write transactions keep a committed action, its journal event and active selection atomic. Revision preconditions reject stale edits. All queries use bound parameters.

New campaigns now start configured Fontenoy drafts with 38 scenario-scale units. Legacy B drafts stay unconfigured until an explicit module-loading command. Rename, clone and archive commit immediately; opening updates last-active selection. Archive preserves a read-only record. Clone creates fresh campaign/entity/objective IDs and a fresh seed, remaps references (including siege targets and map edges), resets started lifecycle metadata, and starts a new journal with a source-campaign reference. The source history remains unchanged. Import retains validated source history and adds a local import event.

Normal data lives in `app.getPath('userData')/campaigns.sqlite` (Windows: `%APPDATA%/maurice-campaign-companion`). A single instance owns each profile. `--user-data-dir` explicitly selects a separate profile, used by tests so they never touch player saves. Startup validates the recovered aggregate and journal; an invalid database is preserved and reported, never silently replaced.

## Transfer and edit semantics

Format v2 exports contain one campaign plus its complete journal, not a faction-filtered view. Legacy format v1 imports remain supported. Aggregate schema v1 lives in `legacy-campaign.ts`; schema v2 adds configured module/settings, contingent provenance, concealment and a started opening state. Mixed-version journal snapshots are validated without rewriting historical payloads. SQLite table layout 001 remains unchanged because the aggregate documents are explicitly versioned; unsupported document versions are rejected.

## Fontenoy setup boundary

The module template is validated JSON. Fact provenance and provisional defaults are documented in `CAMPAIGN_SPEC_FONTENOY.md`. The seed factory accepts an injected UUID generator, and pure setup commands preserve source units while changing assignments/settings. Square IDs are independent of coordinates; scale/edge edits do not regenerate geography or forces.

Named IPC methods load the module into an empty legacy draft, save settings/columns/commanders, and start a reviewed campaign. The renderer cannot submit replacement unit or square arrays through setup IPC. Main revalidates exact force composition, all references and revision preconditions. Module loading refuses legacy custom entities rather than replacing them. Each command and its new event commit atomically.

Setup edits remain undoable (50 steps) until saved. The saved snapshot may have unassigned units during preparation; Start requires complete unique assignments, nonempty positioned columns, valid schedule and explicit house-rule/map acknowledgements. Start defaults to Cancel in a native dialog and records the chosen opening state only. Started/archived setup is read-only. Operational play is enabled separately on Campaign Map; siege progression and victory evaluation remain deferred.

## Operational boundary (Milestone D)

`operations-schema.ts` defines an optional operational extension to aggregate v2. Existing aggregate payloads and journal snapshots remain unchanged until the explicit enable command adds the extension. Export format 2 and SQL table migration 001 remain unchanged; older applications cannot read the extension and should not be used to reopen updated campaigns. Clone removes operational state and remaps the stable setup graph into a new draft.

`operations.ts` owns deterministic route validation, state transitions, date calculation and an allowlisted faction projection. Defaults live in `src/data/operations.v0.1.json`. A named validated operational IPC command accepts only enable/configure/issue/reopen/resolve actions, never replacement campaign arrays. Main revalidates each route against saved rules, ownership, blocks and occupancy. Optimistic revisions and the aggregate/journal transaction cover the complete batch. Resolution requires a native default-Cancel confirmation; no positions or dates change when merely issuing/reopening orders.

Each faction has one sequential phase per turn. Only its columns receive orders; unissued columns hold. After the second faction resolves, the configured date/turn advances. At the deadline the operational phase becomes finished, without a victory result. Hostile destination contact stops movement in the previous square and records ordered engagement candidates; participants are held pending Milestone E. Friendly stacking is allowed, without an invented column capacity. Full command replay validates operational journal transitions on import/recovery.

Zustand keeps up to 50 unissued order edits for undo, preserves them across screens and includes them in discard/close guards. Issued orders are saved and survive restart. Reopening planning preserves the issued version in history. Rule edits are allowed only in planning before orders. The map uses local raster artwork beneath SVG controls; pan uses a scrollable viewport and zoom uses external CSS classes, preserving production CSP.

Faction views use an explicit field allowlist. Concealed opponents are omitted; visible opponents have no private name, unit list or commander details. Opposing orders and full journal snapshots are excluded. Other shared management screens require an explicit switch back to umpire view. A dedicated main-process faction export writes only the committed projection through the atomic JSON writer; full backup export remains an umpire operation. Views are local pass-and-play display filters, not an authentication boundary: the trusted renderer/database still hold the complete aggregate and the operator can select umpire mode.

Import reads a bounded regular file (64 MiB maximum), validates format/module/schema versions, IDs, references and journal continuity before starting the transaction. Duplicate campaign/event IDs are rejected. Export writes a flushed temporary file in the destination directory, then renames it over the destination; failures leave the previous destination intact. File paths are selected by native main-process dialogs and never accepted from renderer payloads. A crash before publication may leave a uniquely named temporary file, but never a partial published export.

Uncommitted form edits live only in renderer memory, with up to 100 title-edit or 50 setup-edit undo steps. Switching screens retains them; switching campaigns or replacing an editor requires explicit discard confirmation. Closing with edits prompts the user. Save commits once; failed saves preserve the draft. Committed actions cannot be undone by rewriting history. The status strip distinguishes pending/uncommitted edits from saved state.

## Tabletop boundary (Milestone E)

`tabletop-schema.ts` defines optional aggregate-v2 scouting rules, contact snapshots and frozen battles/results. `tabletop.ts` validates and deterministically applies commands with a main-generated record ID/timestamp. Main commits the action, receipt, before/after state and audit event atomically with revision preconditions. Recovery/import replays tabletop receipts and compares JSON contents independent of object member order; array order remains significant. Existing histories and SQL layout 001/export format 2 are retained. Clones reset tabletop and operational records into an independent setup draft.

Scouting defaults are versioned JSON. Main generates optional d6 rolls using `crypto.randomInt`; physical/app rolls, modifiers and the umpire's adjudication are recorded. There is no success table or hidden automatic tactical effect. Latest dated contact snapshots drive faction projection with explicit expiry; expired or unknown reports never expose a hidden roster or revive earlier reports. Opposing issued orders remain excluded even when a roster is identified.

Battle declarations validate genuine unassigned candidates, nearby friendly participants, unique commitment, ready units and reinforcement instructions. Frozen roster/commander/origin snapshots form the brief. Movement/scouting cannot reuse committed forces. A separate start command and default-Cancel native result confirmation establish the battle lifecycle. Results require one entry for every frozen unit and commander and do not modify campaign readiness/quality, commander state, siege, exhaustion or victory. Participants remain held for F.

Tabletop draft forms live in Zustand, survive navigation, preserve cancelled/failed result submissions and participate in discard/close guards. Shared Battle Log is gated by umpire view. A narrow native-dialog export accepts only a saved battle ID, revision and HTML/PDF format. Main escapes all player text in an offline HTML document. PDF uses a temporary hidden sandboxed `BrowserWindow`, no preload/Node, restrictive CSP, then `printToPDF` and the bounded atomic writer. Renderer-provided HTML, URLs and filesystem paths are never accepted.

## Strategic boundary (Milestone F)

`aftermath-schema.ts` adds an optional aggregate-v2 extension; `aftermath.ts` applies pure commands through a replaceable strategy registry with defaults in `aftermath.v0.1.json`. `aftermath-state.ts` supplies review/engagement settlement checks without importing the command layer. Existing export format 2 and SQL migration 001 remain unchanged. Named validated `commitAftermathAction` IPC accepts commands, never arbitrary replacement arrays or paths. Main stamps receipts, validates the proposed transition and uses native default-Cancel confirmation for battle effects, commander status changes and finalization. Repository validation, revision checks, snapshots, replayable receipts and events commit atomically.

Broken regular rebuilding preserves `initialQuality` separately and changes current quality to conscript. Scenario validation counts opening qualities while later battle briefs snapshot current qualities. Loss retains the source unit as lost; scheduled recovery marks it ready only at a due checkpoint. Retired rest is optional; tactical disruption and Army Morale never become persistent exhaustion. Commander arrival/status/attachment commands preserve private references without evaluating card effects. Clones remove all three play extensions, restore opening unit qualities/readiness and active officers, and remap the setup graph.

Reviewed battles release participant commitments; historic brief/result snapshots remain immutable. Only columns containing ready units block movement/create new contacts. Explicit post-battle squares settle contacts without inventing retreat/pursuit. Operations pause after the second faction at `pendingTurn`; outstanding encounters/results/reviews must finish before finalization. Recovery, verified supplied investment and victory evaluation run once in that transaction. No new orders/scouting begin during the pause. The last-turn checkpoint does not add an extra campaign turn.

Victory stores the winning conditions, turn and timestamp. Opposing substantive claims use the configured conflict result; the deadline fallback applies only with no substantive claim. A recorded outcome blocks further operational/tabletop/strategic mutations. Renderer drafts reuse the navigation/discard/close guards, survive cancellation/errors and are cleared only after a committed revision. Full backups retain all receipts; faction projections remain allowlisted and exclude private strategic records. See [CAMPAIGN_AFTERMATH.md](CAMPAIGN_AFTERMATH.md) for exact timing and rule proposals.

# Historical reference catalogue (0.14.1)

The immutable `fontenoy-historical-catalogue.json` is validated by `historical-oob-schema.ts`, with globally unique research keys, source/date-aware claims, service-safe hierarchy, aliases and explicit unknowns. These catalogue keys are separate from saved campaign UUIDs. `fontenoy-historical.ts` supplies accent-insensitive reference search and a cited pre-battle context timeline. The renderer consumes this public static reference in a side drawer, filtered by the selected coalition view; it never joins the live enemy roster or changes campaign state.

The original exact 38-unit profile remains supported. Version 0.16.0 adds the separately reviewed regimental profile described above; the research schema itself is not a save migration. Pinned Wikipedia attribution and data-specific CC BY-SA 4.0 terms travel with the renderer data and LICENSE; private WDS material remains excluded.

## Comparable historical formation grouping (0.16.1)

`historical-grouping.ts` pins `reported_subunits_v0.2`: both coalitions target 12 reported battalions or 24 reported squadrons, preserving direct source-listed brigades, separating unknown complements and grouping artillery without conflating gun returns with battalions. It produces 15 French and 13 Allied formations; counter badges show source complements rather than current headcounts. This is a campaign adaptation, not a verified brigade deployment or a combat-power normalization.

`historicalProfile.groupingVersion` is optional without a default, retaining legacy payload/replay compatibility. The explicit native-confirmed `historical-regroup` command accepts fresh formation UUIDs only for untouched, unreviewed historical setups. It preserves roster UUIDs/source references/grades, replaces formation assignments and provisional positions, relocates existing HQs and records the action for replay. Reviewed or progressed games remain intact. No SQLite migration or export-format bump is required.

## Regional maneuvering space (0.17.0)

`regional-map.ts` adds a fixed versioned 36 by 24 topology around the original Fontenoy board, retaining original IDs, original hex/edge objects and order/formation references. Optional `fontenoy.regionalMap` has no default, so legacy payloads and historical receipts replay unchanged. The explicit `expand-regional-map` action is native-confirmed, restricted to active unlocked planning, and available before historical adaptation review because it changes topology without assigning ratings or moving forces. New historical-profile creation uses the expanded topology; legacy profile seeds remain available for compatibility fixtures.

`MapViewport` owns camera state independently of campaign and scene state. Pan/wheel/zoom/centre/fit updates do not redraw or mutate the campaign scene. SVG coordinates remain shared by hexes, routes, formations, intelligence and HQs. Zone highlights are computed once per force, using axial neighbor traversal rather than an exhaustive map scan for every rendered hex. The existing zone semantics remain checked against the previous implementation. Regional geometry validation requires all 864 unique versioned hex positions. Shared schema bounds allow 1200 hexes / 4000 edges. File import/export share a 64 MiB bound; the journal/export format remains unchanged.
